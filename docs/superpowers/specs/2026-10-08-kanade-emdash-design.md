# Kanade 与 EmDash 集成设计

日期：2026-10-08。状态：用户已确认并要求实施；进度见实施记录。

## 目标与版本

在当前 `duanap/index` 空仓库中建立完整的 Astro 博客。保留 Kanade 的视觉风格、Vue 交互、响应式布局和深浅主题，让 EmDash 管理文章、普通页面和上传图片；上传图片自动生成 WebP，前台优先使用 WebP 降低传输体积。成功标准是通过 CMS 发布文章后，刷新前台、RSS 和站点地图即可看到新内容，无需重新构建。

## 方案选择

推荐同一个 Astro 项目集成 Kanade 与 EmDash，采用服务端渲染。内容读写和后台认证使用 EmDash 官方接口，前台沿用 Kanade 的组件。

可替代方案是 CMS 发布后触发 Kanade 静态重建，或让 Kanade 调用独立 CMS 服务。前者需要额外发布流水线，后者需要维护两套服务与跨服务认证。本项目优先保证内容发布即时生效和单项目维护。

部署目标已由用户指定：阿里云轻量应用服务器，2 核 CPU、4 GB 内存，Ubuntu 24.04、宝塔面板 12.0 稳定版；域名为 `duanap.cn`，接入腾讯云 EdgeOne 免费套餐。采用 Node.js、SQLite 和本地媒体存储，不使用 Docker。EdgeOne 提供入口加速与 HTTPS，CMS 和全部数据仍运行在阿里云服务器。

## 运行架构

- `astro.config.mjs` 改为 `output: "server"`，注册 Node standalone 适配器、Vue、React 和 EmDash 集成。
- Vue 与 React 的组件匹配范围明确分开，避免两种渲染器竞争；React 仅处理后台及必要的 CMS 组件。
- `src/live.config.ts` 注册 EmDash 官方 live loader。
- 本地开发默认使用 `data/emdash.db` 与 `data/uploads/`；生产通过环境变量把数据指向站点代码目录外的固定持久化目录，建议 `/www/kanade-data/duanap.cn/`。数据库、上传内容与密钥不提交到 Git。
- 开发使用 `pnpm dev`；生产构建后通过 systemd 启动 Node standalone 服务，由宝塔管理的 Nginx 反向代理。交付不包含 Docker 部署。
- CMS 管理入口保持 `/_emdash/admin/`。用户通过官方初始化流程建立管理员和 passkey，不预置生产账号或密码。
- 使用官方命令生成本地 `EMDASH_ENCRYPTION_KEY`，保留已有密钥；生产通过环境变量注入，文档说明备份要求。

## 阿里云、宝塔与 EdgeOne 部署

### 服务和磁盘

请求路径为：浏览器 → EdgeOne → 源站宝塔 Nginx → `127.0.0.1:4321` 的 Node.js 服务 → SQLite 与上传目录。

- 网站代码建议放在 `/www/wwwroot/duanap.cn/`，Nginx 只做反向代理，不把数据库或环境文件作为静态目录开放。
- systemd 以专用非 root 用户运行一个 Node 服务，配置开机启动、异常退出重启与日志；不同时启动 PM2 或宝塔 Node 管理器管理同一进程。
- 生产端口只绑定回环地址，通过 Nginx 的 80/443 接收请求。CMS 定时发布依赖持续运行的 Node 进程。
- 生产设置 `SITE_URL=https://duanap.cn` 和 `EMDASH_SITE_URL=https://duanap.cn`；构建与运行使用相同站点 origin。提供不含密钥的环境模板，密钥由服务器本地生成并单独备份。
- SQLite 保持单实例部署。更新代码、重新安装依赖或重建不得覆盖持久化目录，也不得重新生成已有加密密钥。
- 2C4G 默认单进程服务。浏览器测试在开发环境运行；构建优先在开发环境完成验证，服务器安装使用冻结锁文件和生产所需依赖，若在服务器构建则限制并行并观察实际内存，不默认增加 swap 或修改系统参数。

### Nginx、HTTPS 与后台

交付适合宝塔网站配置的 Nginx 片段，不覆盖整份面板生成的配置。反向代理保留正确的 Host、X-Forwarded-Host 和协议头，配置 Astro 的允许域名与 EmDash 公共 origin，使 canonical、重定向、CSRF 与 passkey 使用 `https://duanap.cn`。

EdgeOne 与源站之间使用 HTTPS，并验证源站证书。证书申请、续期与域名接入在现有宝塔及 EdgeOne 配置中完成；不假设平台控制台已经配置好。后台通过 `https://duanap.cn/_emdash/admin/` 访问，管理员在正式域名的 HTTPS 页面完成初始化和 passkey 注册。

真实访客 IP 的配置只信任已核实的 EdgeOne 回源地址和由 Nginx 重写的头。未经核实不直接信任客户端传入的转发头；部署文档说明如何同步官方回源网段并验证认证限流。

### EdgeOne 缓存

首版默认对 HTML、RSS、站点地图、预览、认证和 CMS API 绕过缓存，以保证发布后刷新可见，也避免缓存登录会话或草稿。明确设置 `/_emdash/*` 不缓存，并保留请求方法、查询参数、Cookie 与认证头。

带内容哈希的前台 JS/CSS/字体可长期缓存。媒体路径位于 `/_emdash/api/media/file/*`，首版随 CMS 路径一起绕过缓存；如果以后单独开启媒体缓存，需要确认文件权限、响应头和图片替换策略，再添加更具体的规则。页面缓存作为后续可选优化，不是上线的前置依赖。

### 备份与升级

提供 SQLite 一致性备份命令，使用数据库在线备份接口，不在运行时直接复制数据库主文件而遗漏 WAL。备份同时包含上传目录和独立保护的加密密钥，备份文件位于 Web 根目录外。

部署文档包含宝塔计划任务的每日备份、保留周期、升级前备份、回滚代码以及在临时目录验证恢复的步骤。本地磁盘备份方便恢复误操作；如需抵御整台服务器或磁盘丢失，用户可另行把备份复制到站外，不为本次方案引入额外云存储服务。

交付提供 DNS/EdgeOne 接入检查清单，沿用 EdgeOne 控制台实际要求的记录，不猜测 CNAME 目标或自动改写阿里云 DNS。当前没有服务器或控制台访问授权与连接，因此实施在当前仓库完成并验证，生产配置提供可执行说明，不声称已经部署到阿里云。

## 内容模型与迁移

### 文章

`posts` 集合包含标题、摘要、正文、原始文章日期、封面样式、可选上传封面、featured 标记。正文使用 EmDash 原生 Portable Text；分类和标签使用 EmDash taxonomy。文章启用草稿、修订、预览、定时发布与 SEO 能力。

内容适配层将 EmDash 数据映射成 Kanade 的 `PostSummary`，让首页、筛选、搜索、侧栏和文章统计继续使用统一结构。保留原有三个分类及八种装饰封面；上传封面存在时优先展示图片。分类标签来自 CMS，原分类保留翻译，新分类显示编辑者填写的名称。

导入 Kanade 的 24 篇中英日示例文章，保留标题、摘要、日期、slug、分类、标签、封面、featured 和草稿状态。使用解析器转换 Markdown 为 Portable Text，覆盖标题、强调、链接、引用、列表与代码块；转换测试以现有示例内容为依据，不把整篇正文降级为纯文本。

保留 Kanade 一次展示一种语言的行为，默认简体中文。CMS 使用原生语言配置保存三种语言，默认语言不加 URL 前缀；前台仅查询配置语言，不自动混入其他语言。现有 `/posts/{slug}/` 路径保持不变。初始化和后续导入使用稳定标识与跳过冲突策略，重复执行不得覆盖 CMS 中的编辑。

### 页面与媒体

`pages` 集合提供标题和 Portable Text 正文。关于页从 CMS 读取，保留 Kanade 的页面外壳；新增页面通过 `/pages/{slug}/` 展示。导入初始关于内容，提供明确的空内容状态与缺失页面 404。

CMS 上传图片通过 EmDash 媒体路由提供。正文使用官方 `PortableText` 渲染器处理图片、代码与链接；增加匹配 Kanade 的标题锚点、目录和代码样式，保留阅读进度与代码复制。

### 上传图片自动转 WebP

这是用户新增的必需功能，处理在阿里云 Node.js 服务端完成，不依赖 EdgeOne 付费图片处理能力，也不要求作者提前手动转换。

- 静态 JPEG、PNG 自动生成 WebP 衍生文件。默认质量 82，可通过非秘密配置调整；默认最长边 2560 像素，保持比例、较小图片不放大。修正 EXIF 方向，保留透明度，输出不附带 EXIF/GPS 信息。
- 原始文件保留在本地媒体存储中用于恢复，WebP 同样保存到持久化目录。CMS 原始媒体记录保持真实的文件格式；前台文章正文与封面通过统一媒体适配层优先选择生成的 WebP，并输出正确的 `image/webp`、宽高和 URL。
- 已经是 WebP 的静态图片默认不重复有损编码。SVG 保留矢量格式；GIF、动画 WebP 与其他含动画的图片保留原格式，避免丢失动画。实际是否为动画通过文件解码信息判定，不仅依赖扩展名。
- 转换器使用 Node.js 的 sharp，依据实际文件内容解码，限制文件体积和像素数。针对 2C4G 限制同时转换数量，默认一次一张；使用临时文件和原子完成步骤，避免暴露半写入的文件。
- 新上传触发转换；替换图片使旧衍生文件失效并重新生成，删除媒体同步清理衍生文件。转换结果按源内容标识，避免把旧 WebP 用于新图片；重复触发不重复处理同一份内容。
- 转换失败时保留可读原图，记录明确失败原因，前台可回退原图；不把失败记录为转换成功。转换、原图读取和删除继续遵守原媒体访问权限，衍生文件不通过无鉴权的额外目录暴露。
- EmDash 1.2.0 的 `media:beforeUpload` 钩子只有文件元数据，源码明确指出它不会改变上传字节。因此不能仅改扩展名或 MIME 类型冒充转换。实现以官方媒体事件触发独立的服务端衍生文件处理，另行保存结果映射，不修改 EmDash 包源码或原记录来掩盖格式差异。
- 后续渲染采用尺寸合适的图片、显式宽高与非首屏懒加载，避免每次访问都重新编码。公开图片的 EdgeOne 缓存仍按前述媒体规则处理，转换本身无需开启 CDN 缓存。

主题颜色、布局、导航、作者信息、友链和界面语言继续使用 Kanade 配置文件；留言墙保留原有浏览器本地存储行为。本阶段的 CMS 管理范围是文章、普通页面和媒体。

## 路由、数据一致性与错误处理

- 文章详情从静态 `getStaticPaths` 改为按 slug 查询 CMS，公开请求只显示已发布内容。
- 首页、列表、侧栏与搜索使用同一批公开文章数据；处理官方分页结果，不能只读取默认第一页而漏掉文章。同一次请求复用查询，避免各组件重复读取整库。
- 预览走 EmDash 官方认证机制；公开 RSS、站点地图与列表始终排除草稿、归档和未到发布时间的文章。
- RSS 与站点地图在请求时生成，保留 `/rss.xml`、`/sitemap.xml` 和 `/sitemap-index.xml` 的兼容入口。后台及认证路由不进入站点地图。
- 保留旧文章和留言跳转路径；不存在的文章返回 HTTP 404。
- 数据库读取失败显示实际错误状态，不能伪装成空文章列表或回退到旧 Markdown 数据。
- canonical、Open Graph、RSS 与站点地图统一读取配置的公共站点地址；反向代理部署同时配置 EmDash 的公共 origin。
